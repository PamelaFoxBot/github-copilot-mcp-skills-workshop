MCP concepts

Why coding agents need tools

Your goal
→
Language model chooses a tool
→
Agent runtime executes it
→
Result becomes context
The model proposes. The host executes, permissions constrain, and you approve.
The LLM never directly calls an API. It emits a structured tool request that the runtime decides whether and how to execute.

What MCP standardizes

You
→
MCP host
GitHub Copilot
→
MCP client
→
MCP server
Learn or GitHub
  • The client initializes a connection and discovers capabilities dynamically.
  • The server publishes schemas that describe names, arguments, and behavior.
  • MCP does not replace authentication, authorization, or user approval.
One host can run multiple MCP clients, usually one connection per configured server.

Servers can expose more than tools

Tools

Functions an agent can choose and call with structured arguments.

Example: search GitHub issues.

Resources

Read-only context that a user or client can browse and attach.

Example: repository contents.

Prompts

Reusable prompt templates published by a server.

Example: a guided analysis prompt.

Support varies by host. Tools are the common denominator.

Microsoft Learn MCPGitHub MCP

Documentation workflows

Use the right Learn tool

QuestionToolWhy
Where is the current guidance?microsoft_docs_searchSemantic discovery across official docs
What does the full reference say?microsoft_docs_fetchComplete selected page and API details
What does working code look like?microsoft_code_sample_searchOfficial snippets filtered by language
Search, select, fetch, compare, cite. A search snippet is rarely the end of the investigation.

Tool discovery and approval

At connection time

  • Review server URL or command.
  • Decide whether to trust the server.
  • Client discovers current schemas.
  • Enable only relevant tools.

At call time

  • Review tool name and arguments.
  • Check whether data leaves your environment.
  • Confirm the result and citations.
  • Deny or refine surprising calls.
Trusting a server to start is not blanket approval for every action. Approval behavior differs by host and user settings.

Authentication

OAuth establishes the GitHub identity. SSO or token policy may also apply.

Authorization

The account and repository permissions determine what each call may read or change.

GitHub toolsets reduce noise and risk

ToolsetExamplesWorkshop use
contextget_meIdentify the active account before acting
repossearch repositories, read files, list commitsRemote code research
reposread files, create branches, push filesResearch and commit the contribution
pull_requestsread, review, create PRsSubmit the tested fix upstream

The default server includes context, repos, issues, pull requests, and users. CLI starts with read-only tools by default.

Read and write are different risk classes

Read

  • Can expose private source or metadata
  • Can ingest untrusted issue text
  • Still deserves review
  • Example: get_file_contents

Write

  • Changes shared state
  • Can notify or affect other people
  • Verify target and payload
  • Example: create_pull_request
Authenticated does not mean approved. Ask to see exact write content before allowing the call.

A practical contribution workflow

Verify fork and research upstream
→
Edit and test locally
→
Commit to fork branch
→
Open upstream PR

Different stages use different tools in the same agent loop. GitHub MCP does not replace local editor or terminal tools.

Security and next steps

A five-question approval check

  1. Source: Do I trust this server or skill?
  2. Identity: Which account and organization policy apply?
  3. Scope: Which systems and private data can the tool access?
  4. Operation: Is this read-only, mutating, or destructive?
  5. Payload: Are the target, arguments, and outgoing data correct?
Repository content, tool descriptions, and fetched text can all carry prompt injection. Treat external content as untrusted.

Takeaways

  • MCP gives coding agents a standard way to discover external capabilities.
  • Public and authenticated servers have different setup and risk profiles.
  • Tool calls are inspectable, controllable, and constrained by real permissions.
  • Good workflows mix remote MCP tools with local editing and validation.
  • Agent skills make those workflows reusable without replacing MCP.
  • Least privilege and deliberate approval are part of the engineering work.
